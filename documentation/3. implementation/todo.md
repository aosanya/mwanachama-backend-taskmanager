| W12 | 🐞 **BUG — `PUT /workflow-runs/{runID}/last-event-at` accepts any caller-supplied string and lets a caller permanently hide a run from the stale-run watchdog.** `TouchWorkflowRunLastEventAt` (`workflow_run.go:353-356`) writes the request body's `timestamp` field straight into the `last_event_at` column via `UpdateColumn`, with no parsing or format validation. `ListWorkflowRunsStaleSince`/`ListWorkflowRunsStepStaleSince` (`workflow_run_watchdog.go`) compare that column against a cutoff with a **plain lexicographic string comparison** (`last_event_at < cutoffStr`), which only sorts chronologically when the stored value is itself a zero-padded RFC3339 string. Demonstrated through the real `routes.Routes(tm)` mux (`routes/w12_last_event_at_watchdog_evasion_test.go`): an untouched run correctly appears in `GET /workflow-runs/stale?cutoff=9999-01-01T00:00:00Z` (any real timestamp sorts before a year-9999 cutoff); a second run touched via `PUT .../last-event-at` with body `{"timestamp":"zzzz-not-a-real-timestamp"}` gets a clean `204`, and the identical stale-since query with the same far-future cutoff **no longer returns it at all** — `body=null` where the untouched run's body correctly lists it. Since this column is what drives the AI-failure-recovery watchdog (this repo's own CLAUDE.md: "the watchdog... currently lean\[s\] on Arango's traversal; rebuild them as recursive CTEs" — the comparison itself was rebuilt, but never given input validation), any caller of this route — including a misbehaving or malicious agent — can wedge a run so it is never flagged as stale again, no matter how long it actually goes quiet. | 📋 | Found by the fleet integration-test sweep (loophole catalogue #3: "a default that does not match reality" — the lexicographic-sort assumption silently breaks the moment the column isn't a real RFC3339 string). Pinning test committed in `routes/w12_last_event_at_watchdog_evasion_test.go` (`TestWorkflowRun_TouchLastEventAtWithGarbageStringEvadesStaleWatchdog`) — asserts the *current* broken behavior (baseline run reported stale, touched run invisible) and documents in its own comment what must flip once fixed: either `TouchWorkflowRunLastEventAt` should reject a non-RFC3339 `ts`, or the watchdog queries should stop relying on string ordering (e.g. a real `TIMESTAMP`/`TIMESTAMPTZ` column, or parsing `ts` before storing and re-formatting canonically). `go test ./...` and `go test -tags=integration ./...` both green with this test added. |
| W11 | 🐞 **BUG — `POST /tasks`, `POST /projects` and `POST /todos` all honor a caller-supplied `id`, and re-posting the same id 500s instead of 409.** Driven through the real `routes.Routes(tm)` mux (`routes/w11_caller_supplied_id_test.go`): `POST /tasks` with body `{"id":"attacker-chosen-task-id","title":"probe task"}` returns `201` with `"id":"attacker-chosen-task-id"` in the response — the server-generated UUID `TaskRow.BeforeCreate` mints is never used, because `task_impl_task.go`'s `CreateTask` never clears `task.ID` before calling `gormstore.TaskToRow(task)`, and the `BeforeCreate` hook only mints `if r.ID == ""` (`gormstore/task.go:50`). Same gap, same shape, in `project.go`'s `CreateProject` (never clears `p.ID`) and `todo.go`'s `CreateTaskTodo` (never clears `todo.ID`) — confirmed by the same probe against `POST /projects` and `POST /todos`. Re-`POST`ing the identical body a second time hits the sqlite/Postgres primary-key unique constraint and surfaces as `constraint failed: UNIQUE constraint failed: probe_tasks.id`, which `routes/errors.go`'s `writeTaskErr` does not recognize (its `errors.Is(err, ErrTaskAlreadyExists)` 409 arm exists but `CreateTask` never returns that sentinel on this path) — so the caller gets an opaque `500 {"error":"task manager store unavailable"}` instead of a clean `409`.
