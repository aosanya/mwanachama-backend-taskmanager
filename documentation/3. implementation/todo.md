| W15 | 🐞 **BUG — `IncrementFailureBudget` is documented as atomic ("atomically increments failure_pipelines_used") but is a plain read-modify-write with no CAS guard, so concurrent recovery-run increments on the same root run lose updates.** `workflow_run_failure_budget.go:48-82` reads the root run's current `FailurePipelinesUsed`/`CountedChildRunIDs` via `GetWorkflowRun`, computes `newUsed`/`newCounted` in Go, then issues an unconditional `UPDATE ... WHERE id = ?` with no `WHERE failure_pipelines_used = ?` optimistic-concurrency check and no transaction wrapping the read+write — the identical TOCTOU shape already filed as `mwanachama-backend-assetmanager`'s A13 (`CommitHold`/`ReleaseHold`) and the shape `mwanachama-backend-git`'s `advanceBranchHead` was fixed to guard against. Demonstrated through the real `routes.Routes(tm)` mux (`routes/w15_failure_budget_increment_race_test.go`, sqlite pool pinned to one connection so goroutines share the same in-memory database): created a root run, set its budget to 10, then fired 5 concurrent `POST /workflow-runs/{rootRunID}/failure-budget/increment` calls with 5 **distinct** `child_run_id`s (a legitimate, non-duplicate case — this is not testing the method's own documented idempotency-on-repeat-id behavior, which is correct). Every one of the 5 concurrent calls returned `200 used:1` — a genuinely new child, and the increment should have landed 5 times — and the run's final persisted state shows `failure_pipelines_used=1`, `counted_child_run_ids=["child-1"]`: only one of five legitimate increments survived, every run of the probe (3/3 runs, same result). This defeats the whole purpose of the counter — a mounting service dispatching several recovery pipelines concurrently under load will systematically undercount `failure_pipelines_used`, meaning `exhaustedAt`'s `used > budget` gate can stay open past the real number of pipelines actually dispatched, exactly the AI-failure-recovery runaway this repo's own CLAUDE.md flags failure-budget accounting as existing to prevent ("rebuild them as recursive CTEs... this is new transactional design, not a mechanical port"). Fix shape: a CAS-style `UPDATE ... WHERE id = ? AND failure_pipelines_used = ?` retried on `RowsAffected == 0`, or wrap the whole read-modify-write in one `db.Transaction(...)` with a row lock, matching the fix already suggested for assetmanager's A13. | 📋 | Found by the fleet integration-test sweep (loophole catalogue: concurrent-actor TOCTOU on a documented-atomic counter, same class as `mwanachama-backend-assetmanager`'s A13). | W14 | 🐞 **BUG — `RollbackWorkflowRun`'s documented "4-step compensation sequence" is not enforced anywhere: `DELETE /workflow-runs/{runID}/artifacts` and `PUT /workflow-runs/{runID}/status` are independently-reachable routes over its middle and final steps, so either can be called alone, in any order, on a run at any status.** `workflow_run_rollback.go`'s own doc comment states the sequence as "rolling_back → compensate cross-service artifacts → compensate own artifacts → rolled_back", but nothing outside `RollbackWorkflowRun` itself follows or enforces that order — the two primitives it calls (`DeleteWorkflowRunArtifacts`, `UpdateWorkflowRunStatus`) are each mounted as their own top-level route in `routes/workflowrun_lifecycle.go`/`routes/workflowrun.go` with no cross-check between them. Demonstrated through the real `routes.Routes(tm)` mux in two directions (`routes/w14_rollback_sequence_bypass_test.go`): **(1)** `TestWorkflowRun_DeleteArtifactsBypassesRollbackStateMachine` — a run driven to `in_progress` (never touched `rolling_back`) with one Task linked; `DELETE /workflow-runs/{runID}/artifacts` returns a clean `204` and the Task is reset to `pending` with `workflow_run_id` cleared (`GET /workflow-runs/{runID}/tasks` returns `[]`), while `GET /workflow-runs/{runID}` still reports `"status":"in_progress"` throughout — `DeleteWorkflowRunArtifacts` (`workflow_run_rollback.go:78-81`) only calls `GetWorkflowRun` to confirm the run exists, no `CanTransitionTo`/status guard at all. **(2)** `TestWorkflowRun_ForcedStatusToRolledBackSkipsArtifactCleanup` — a run with a linked Task driven `in_progress → failed → rolling_back` via three separate `PUT .../status` calls (never once calling `DeleteWorkflowRunArtifacts`), then `PUT .../status {"new_status":"rolled_back"}` succeeds (`200`, since `rolling_back → rolled_back` is a legal `WorkflowRunStatus.CanTransitionTo` transition) — the run now reports the terminal `"rolled_back"` status while the linked Task's `workflow_run_id` is still set to the run's own id, i.e. the Task was never compensated. Together these show the two halves of "rollback" can be driven fully independently: artifacts silently wiped while status lies "in_progress", or status flipped to the terminal "rolled_back" while artifacts sit untouched — either is a worse state than the sequence's own documented partial-failure path (`rollback_failed`), because neither surfaces as an error at all. Answers this sweep's specific question about atomicity: the 4-step sequence was never atomic even conceptually — steps 1/3/4 are three separate top-level DB commits by the file's own design (see its doc comment: "not part of step 3's transaction"), and this finding shows steps 3 and 4 are not even guaranteed to run together, or in order, or at all. | 📋 | Found by the fleet integration-test sweep, driving the real mux (loophole catalogue #10: "rejection paths' state-after" broadened to "ordering paths' state-after" — no single call is rejected, but the composite the sequence promises never actually happens). Two pinning tests committed in `routes/w14_rollback_sequence_bypass_test.go` asserting the *current* behavior, each documenting in its own comment what must change once fixed (most likely: `DeleteWorkflowRunArtifacts` should require `run.Status == rolling_back` before touching anything, and/or `UpdateWorkflowRunStatus` should refuse `rolling_back → rolled_back` except from inside `RollbackWorkflowRun`'s own call, or fold step 3 into step 4's write). Ruled out separately in the same investigation: `ErrForeignRunDependency` (ErrForeignRunDependency IS correctly enforced through the real `DELETE .../artifacts` route — confirmed `409` with the exact cross-run dependency message when a depended-upon run's artifacts are targeted) and `DeleteWorkflowRunArtifacts`'s own internal transaction (task resets + todo soft-deletes are atomic with *each other*, per its existing `gorm.DB.Transaction` wrapper — not in question here). `go test ./...` and `go test -tags=integration ./...` both green with these tests added. |
