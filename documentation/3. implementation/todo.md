| W23 | 🃏 **A card has no place in its column — `Task` carries no rank, so a board cannot be ordered by hand.** `models.Task` has `Status`, `Priority`, `DueAt`, `EstimatedHours` and no position field of any kind, while `models.TaskTodo` *does* carry `Ordinality` (sorted at `workflow_run.go:253`) — so the checklist inside a task can be ordered and the tasks themselves cannot. A board can therefore only ever sort a column by created-at, priority or due date; "put this one above that one", the single most-used gesture on a kanban, has nowhere to be stored, and two cards created in the same second have no stable order at all. Fix shape: a rank on `Task` — a fractional index (string or float, so an insert between two neighbours never rewrites the column) is the cheap version; an integer with periodic re-balance is the other. Whichever lands, `ListTasksInProject` has to return it and order by it, or the storage is decorative. | 📋 | Filed 2026-09-28 while deciding which backend manages a backlog for the agency-conformance work (`developer/documentation/4. qa/agencies/todo.md`, AGX8). Not a bug — a missing capability, filed because the answer to "which backend holds a kanban" is this one, and this is the first thing it lacks. |
| W24 | 🚦 **The columns are the lifecycle, not the board's — and `CanTransitionTo` refuses the ordinary kanban moves.** `TaskStatus` is a closed eight (`pending`, `in_progress`, `blocked`, `awaiting-direction`, `completed`, `failed`, `cancelled`, `split`) with a hand-rolled transition table, which is right for an agent-run pipeline and wrong for a board a team arranges: the columns are the same for every project, a team cannot name its own (`Backlog`/`Next`/`Doing`/`Review`/`Done`), and three of the four statuses in that list have no equivalent here at all. The transition rules then refuse moves a board treats as routine — `pending → completed` is illegal (a card cannot be dragged straight to Done; it must pass through `in_progress`), and `completed` and `cancelled` are terminal, so **a card can never be dragged back out of Done to reopen it**. Decide one of two: a board object whose columns map onto statuses (the board is a view, the lifecycle stays authoritative, and a drag that has no legal transition is refused with a reason the UI can show), or the lifecycle *is* the board and reopening gets a legal path (`completed → in_progress`) added deliberately. Either way it is a decision to record, not a default to inherit. | 📋 | Filed 2026-09-28, same pass as W23. The transition table is documented on `CanTransitionTo` in `models/task.go`; the terminal-state reading was taken from the code, not the comment. |
| W25 | 🧮 **No board object, no WIP limit, and no swimlane — `Project` is a container, not a board.** `models.Project` carries `Name`, `ProjectName` (slug), `Description`, `RepoName`, `GithubRepo` and `TaskPrefix` — repository-shaped fields for an engineering backlog, with nothing describing how the work is displayed or governed. There is no column set, no work-in-progress limit per column (the one rule that makes a kanban a kanban rather than a list with headings), and no swimlane. `ListTasksInProject(ctx, projectID)` does load a project's tasks, so a board can at least be fetched — but `TaskFilter` (status, priority, workflow-run id, limit) has no project field, so any filtered board view has to load the project whole and filter in the caller. Depends on W24: if a board object lands there, the limit and the swimlane belong on it; if the lifecycle stays the board, they belong on `Project`. | 📋 | Filed 2026-09-28, same pass as W23/W24. Note this repo's declared-domain conversion was in flight the same day (`taskmanager.blueprint.json`, `spec/`, `store.go` all untracked in the working tree) — whatever shape these three rows take should be declared in the blueprint rather than added as Go fields after it lands. |
